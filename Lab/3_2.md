Lab 3.2 — Security Context Lockdown (business domain — movie-service)

Làm ở namespace lab trước (Pod độc lập, không đụng Deployment thật) — nếu chạy ổn mới cân nhắc áp lên movie-booking, vì readOnlyRootFilesystem có thể làm hỏng thứ gì đó bất ngờ nếu chưa test kỹ.

Đề bài

Lockdown movie-service với:

runAsNonRoot: true (không cần chỉ định UID cụ thể — Dockerfile đã có USER app, k8s chỉ cần biết UID đó khác 0)
readOnlyRootFilesystem: true ở container
allowPrivilegeEscalation: false
Drop toàn bộ Linux capabilities (drop: ["ALL"])
Điểm mấu chốt cần lường trước: readOnlyRootFilesystem sẽ làm hỏng thứ gì?

movie-service ghi log ra /var/log/app/app.log (đã mount emptyDir từ Phase 4) — volume mount vẫn ghi được bình thường dù root filesystem readonly, vì volume là 1 mount point riêng, không thuộc "root filesystem" của container. Chỉ cần đảm bảo mọi đường ghi file đều đi qua volume, không ghi thẳng vào filesystem gốc của image.

Bước 1 — Tự viết checklist (thử trước khi xem đáp án)
 spec.securityContext.runAsNonRoot: true
 spec.securityContext.fsGroup: 1000 (đảm bảo volume app-logs ghi được bất kể UID chính xác của user app trong image là gì)
 containers[0].securityContext.allowPrivilegeEscalation: false
 containers[0].securityContext.readOnlyRootFilesystem: true
 containers[0].securityContext.capabilities.drop: ["ALL"]
 Volume app-logs (emptyDir) vẫn mount vào /var/log/app như cũ
Created a file, ran a command, read a file
Created a file, ran a command, read a file
Bước 2 — Apply và verify
bash
kubectl apply -f labs/lab-3.2/manifests/locked-down-pod.yaml
kubectl get pod movie-service-locked-down -w
# phai len Running binh thuong, KHONG bi CrashLoopBackOff
Bước 3 — Xác nhận thật sự readonly (không chỉ tin vào YAML)
bash
# Thu ghi vao root filesystem - PHAI BI TU CHOI
kubectl exec movie-service-locked-down -- touch /test-file
# ket qua mong doi: "touch: /test-file: Read-only file system"

# Nhung ghi vao volume (LOG_FILE_PATH) van OK binh thuong
kubectl exec movie-service-locked-down -- cat /var/log/app/app.log
# phai thay log that, khong loi gi

# Xac nhan dang chay khong phai UID 0
kubectl exec movie-service-locked-down -- id
# uid PHAI KHAC 0 (khong phai root)
Bước 4 — Xác nhận capabilities đã bị drop hết
bash
kubectl exec movie-service-locked-down -- cat /proc/1/status | grep Cap
# so sanh voi 1 Pod thuong (khong lockdown) - CapEff phai la 0000000000000000
Bonus (thảo luận, không bắt buộc làm) — vì sao KHÔNG áp readOnlyRootFilesystem cho nginx-ambassador dễ như app

Nginx (kể cả bản unprivileged) mặc định cần ghi vào /var/cache/nginx/*, /var/run/nginx.pid, /var/log/nginx/* — nếu bật readOnlyRootFilesystem: true cho container này mà không mount thêm emptyDir vào đúng 3 đường dẫn đó, container sẽ crash ngay khi start. Đây là lý do thực tế security hardening luôn phải test kỹ theo từng loại image, không có công thức áp dụng y hệt cho mọi container.

Dọn dẹp
bash
kubectl delete pod movie-service-locked-down

Chạy thử, báo lại đặc biệt Bước 3 (touch có bị từ chối đúng như dự đoán không, id có ra UID khác 0 không) — xong mình sang Lab 3.3 — ServiceAccount & RBAC.
